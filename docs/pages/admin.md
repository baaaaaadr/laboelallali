# Page: /admin

## Purpose
Staff space, organized into **seven tabs** (Tableau de bord · Patients · Demandes · Médecins · Relances · Tester · Équipe) so it stays usable on mobile as it grows. Five jobs:
1. **Search patients, attach a CyberLab identity, and attach relatives' dossiers** — the **Patients** tab. A multi-field search (email, name/prénom, phone, date of birth, `requester_id`) finds the patient; picking a result shows their account creation date + date of birth and prefills the attach form, which merges `requester_id` + `type` onto their account (browser equivalent of `functions/scripts/seed-requester.js`). Replaces the old exact-email-only lookup.
2. **Fulfill patient access requests** — the **Demandes** tab lists patients with a `pending` request; staff verifies identity (face-to-face) and attaches `requester_id` + `type` to activate access. A request lands here **two ways**: the patient tapped "Demander l'accès" on `/resultats`, OR it was **auto-created at signup** (`autoRequestResultsAccess()`, see `docs/pages/login.md`). Dr Aziz uses this queue as the **new-registrant outreach list** — the front desk phones each new signup to offer/explain the online-results service — so it is intentionally NOT limited to explicit requests.
3. **Manage the team** (roles) — the **Équipe** tab (managers only): owners add/remove admins; owners and admins add/remove staff (stagiaires).
4. **Test a requester_id** (onboarding probe) — the **Tester** tab lets staff run a live CyberLab call for an arbitrary `requester_id` + `type` and preview what the patient would see (dossier list + analyses), BEFORE asking the patient to log in on their own device. Each dossier has a **"Voir le PDF"** that fetches that single PDF exactly like the patient's "Voir" — so staff also catch a failing/empty PDF (the on-demand PDF is where onboarding actually breaks). Patient names are scrubbed server-side. Independent of the email lookup (the patient may not have an account yet).

   **The three outcomes are the diagnostic, and each is rendered as a `VerdictPanel` (what was seen · what it means · the one thing to do next), not a bare one-liner** — the panel lives in `src/components/ui/VerdictPanel.tsx` (extracted from the local `TestVerdict` this page used to define, so `/resultats` shows the patient the same three-part message; see `docs/pages/resultats.md` §4h) — the tab exists to make the front desk autonomous, and a trainee facing "Aucun résultat" had nowhere to go. Confirmed experimentally on 21/07/2026 (see `docs/integrations/diagnostic-dossiers.md` §4):
   - **404 `not-found`** → the patient is unknown to the lab replica. Either the number is wrong, **or their CyberLab account was never created in Qalam** — the API only knows "published" patients, and activating access in *this* app does not publish anyone. The front desk does normally perform that Qalam step when it fulfils a request (all 10 app-linked patients resolve fine), so this verdict catches the **occasional omission** — which is otherwise invisible to everyone, since neither the patient nor the staff gets an error. Do NOT read it as a systemic failure, and do not tie it to the dashboard's 0 % usage rate: usage tracking only started on 2026-07-20.
   - **200 + empty `pdf_base64`** → the dossier row exists but the document does not. The patient sees the line and cannot open it; the lab must republish that dossier.
   - **200 + valid PDF** → nothing to do.

5. **Track adoption** — the **Tableau de bord** tab (default): how many patient accounts exist, how many have their results access activated, how many are pending, and — the point of it — **who actually uses their account vs who is dormant**, with a one-tap WhatsApp relance for dormant patients. Sold to Dr Aziz as "Version 2" (base + suivi d'utilisation), the level that crosses into a small CNDP commitment.

It does NOT create patient accounts (patients sign up themselves). It never persists medical results — the test preview is fetched on the fly, held in React state only, and the response carries `Cache-Control: no-store`. The **only** usage datum stored anywhere is `users/{uid}.lastResultsAt` (a date, see below).

## Layout — four tabs
`activeTab` (`dashboard|patients|requests|doctors|relances|test|team`, default `dashboard`) selects one section; only that section renders. **Access split:** `dashboard` and `team` are added to `tabs` only when `isManager` (level ≥ 2) — a guard effect bounces a stagiaire off the default `dashboard` onto `patients`. Everything else, **including `relances`**, is staff-level: chasing patients is the front desk's job, so the relance list deliberately lives outside the managers-only dashboard (own tab, own callable `adminListDormant`). The tab bar uses the shared `TabsNavigation` (`src/components/features/catalog/TabsNavigation.tsx`, `TabItem {id,label,icon,count?}`, RTL-aware, horizontal-scroll on overflow) in a plain in-flow wrapper (`border-b`) — **not sticky** (deliberate): it scrolls away with the page so it consumes zero fixed screen space; to change tab, scroll back to the top. The `team` tab is only added to `tabs` when `isManager`; the `requests` tab shows a live count badge (patient access + relative requests), the `doctors` tab its own (doctor requests).

### Width policy (septembre 2026) — `CADRE` + `CONTENT_WIDTH`
The space used to sit in `max-w-2xl` (672 px), so a 1500 px screen showed a narrow ribbon. The frame is now `CADRE = max-w-[1536px]` (the Tailwind `2xl` breakpoint, written as an explicit value because `max-w-screen-2xl` was dropped in Tailwind v4), and **each tab declares its own useful width** in the `CONTENT_WIDTH` map:
- **Data tabs take the full frame** — `dashboard`, `relances`, `requests`. This is where the room pays: the dashboard is **37 % shorter** at 1536 px (5329 -> 3344 px of scroll, measured with the preview bench below).
- **One exception inside `requests`:** the `RelativeRequestsSection` block (rattachement d'un proche) is wrapped in `max-w-4xl` at its call site in `page.tsx`, not in the component. Those cards are an identity VERIFICATION — probe the dossier, compare the names, tick the box — handled one request at a time, so they get a reading measure while the plain pending queue above them spreads over two columns. Two neighbouring lists, two different jobs.
- **Form tabs keep a short measure** (`max-w-4xl`) — `patients`, `doctors` (one card per doctor, with actions), `test`, `team`. A 1500 px-wide text input helps nobody, and past ~75 characters a line of prose becomes hard to track.

Content is **left-aligned inside the frame**, on the same edge as the title — a narrow tab reads as a column that stops, not as a centred block that shrank. These classes are **ceilings**: below 1024 px nothing changes, mobile is untouched (verified: 0 px of horizontal overflow at 390 / 360 / 320 px).

**Both constants hold literal class strings on purpose.** Tailwind v4 scans source text; a computed class name would never be emitted.

### Grid structure of the dashboard
Each narrative section of `AdminDashboard.tsx` is a grid rather than a stack. Reading order is preserved — a CSS grid flows left to right then top to bottom, exactly like the stack it replaces:
- sections 4 and 5 (evolution, ou ca bloque) -> `grid xl:grid-cols-2`
- section 6 (qui utilise : âge, fréquence) -> `grid md:grid-cols-2` since 24/09/2026 (its third card, « Accès médecins », became section 6b); section 7 (reactivite) -> `grid md:grid-cols-2 xl:grid-cols-3`. The lone `ChartCard` that used to sit above an inner 2-column grid was **merged into it**; do not re-nest a `md:grid-cols-2` inside one of these, it yields four cramped columns
- **section 6b « Les médecins »** (24/09/2026, owner's request « voir à quel point ils consultent les dossiers de leurs patients ») -> one full-width `ChartCard`: three figures (médecins activés, actifs sur 30 jours, bilans ouverts ce mois-ci), then one row per doctor — last visit, days of visit and reports opened this month, reports opened in total. A `<table>` from `sm` up (`data-testid="dash-doctors"`), **one block per doctor on phones** (`dash-doctors-list`: measured, the five columns needed a sideways scroll at 390 px). Name and code sit in a flex row with a gap, never a margin on the `dir="ltr"` code (in Arabic that margin lands on the wrong side and glues the code to the name). When team accounts are left out it says how many (« Comptes de l'équipe non comptés ici : N ») and, if they are the only doctors, « Aucun médecin en dehors des comptes de l'équipe » instead of « Aucun médecin activé ». Counts only — never a patient, never a dossier. Covered by `scripts/test-practitioner-ui.js` M19; `scripts/preview-admin-dashboard.js` has doctors in its fixture.
- section 8 (relances) -> `grid sm:grid-cols-2 lg:grid-cols-3`
- section 9 (listes repliees) -> `grid xl:grid-cols-2 items-start`

All rows carry `items-start`: a short chart gains nothing from being padded out to its tallest neighbour. `RelancesTab` and the pending-requests queue are grids of bordered cards — `divide-y` does not work in a grid, hence the per-card border, which also makes the two lists look alike.

## Role model (single `role` field on `users/{uid}`)
Hierarchy, higher does everything lower can:
- **`owner`** (level 3): manage admins + everything below. (Bootstrapped: hassanelallali@gmail.com, azizelallali@gmail.com.)
- **`admin`** (level 2): add/remove **staff** + encode. Cannot touch admins/owners.
- **`staff`** (level 1, "stagiaire"): encode `requester_id` with type **`patient`** + test a `requester_id` (any type — read-only, and the front desk already sees every result in Qalam).

### Non-patient types are admin-only (23/09/2026)
A `medecin`/`correspondant` identity opens a whole **roster of named results** — and since 23/09/2026 a real prescriber code answers on the lab server. So:
- `adminSetRequester` / `adminFulfillAccessRequest` accept a non-patient type **only from an admin** (`assertOwnTypeAllowed`, `permission-denied` otherwise); the Demandes and Patients selects only offer `Médecin`/`Correspondant` when `isManager`.
- A **relative is always a patient dossier**: `adminLinkRequester` / `adminFulfillRelativeRequest` refuse any other type (`assertRelativeType`), and the two attach forms (`LinkedRequestersCard`, `RelativeRequestsSection`) no longer show a type selector. A doctor's code attached as a "relative" would have dropped his roster into the family tabs, with a dossier-holder email announcing « un proche peut consulter vos résultats ».
- Doctors get their access through the separate **accès médecin** (`adminSetPractitioner`, admin level) — see below and `docs/pages/mes-patients.md`.
- Audit on 23/09/2026: every existing identity (58 own + 4 relatives) was of type `patient` — nothing to migrate.

`levelOf(role)` = `{owner:3, admin:2, staff:1}`. Page sections: encode + test-a-requester_id (level ≥ 1), team management (level ≥ 2), the "add admin" form + admin-removal (level = 3).

The role gate (`LEVEL`/`levelOf`/`requireLevel`) + `REGION` live in a shared leaf module `functions/src/admin/roles.ts`, imported by both `adminPatients.ts` and the CyberLab staff callable `adminTestResults.ts` (single source of truth).

## Access control (defense in depth)
1. **Page gate:** requires `user`; unauthenticated → redirect to `/[lang]/login`. If `level < 1` → "Accès refusé" card.
2. **Server gate:** every callable re-computes the caller's level from `users/{uid}.role` (never trusts the client) via `requireLevel(request, min)`. Hiding UI is not the boundary — the functions are.

## Backend (Cloud Functions — `functions/src/admin/adminPatients.ts`)
All region `europe-southwest1`, all guarded by `requireLevel`:
- `adminLookupPatient(email)` (≥staff) → patient profile/identity, or `{ found:false }`. Kept for compat; the UI now uses `adminSearchPatients`.
- `adminSearchPatients(query)` (≥staff) → `{ results: SearchResult[], truncated }`. Scans `users` (`.limit(SCAN_LIMIT=5000)`, Admin SDK bypasses rules) and matches the normalized query (lowercase + strip diacritics) as a substring of `fullName`/`email`, equality/inclusion on `requester_id`, phone digits (query ≥ 4 digits), or `dateOfBirth`. Exact email/`requester_id` ranked first; capped at `MAX_RESULTS=25` (`truncated` flags overflow). Email fallback via `getUserByEmail` for a profile-less account. Returns `createdAt`/`dateOfBirth` for display. In-memory match (Firestore has no substring search) — see scale caveat in Notes. Never logs PII.
- `adminSetRequester(email, requester_id, type)` (≥staff) → merges `{requester_id, type}` onto `users/{uid}` (Admin SDK, bypasses rules). Validates `type ∈ {patient,medecin,correspondant}`; **a non-patient type requires ≥admin** (see "Non-patient types are admin-only").
- **`adminLinkRequester(uid, requester_id, type, label)`** (≥staff) → attaches a RELATIVE's dossier to an account ("ayant droit"). Returns `{success, links, holderNotified}`.
  - Targets by **`uid`**, not email (the Patients tab already holds it; email is a weaker key).
  - Uses a **transaction with an upsert keyed on `requester_id`** — NOT `arrayUnion`, which dedupes by deep equality and would create a duplicate row when a label is corrected.
  - Writes **both** `linkedRequesters` (the rows) and `linkedRequesterIds` (flat ids). The flat array exists because `array-contains` cannot query a sub-field of a map inside an array, and "which accounts can read this dossier?" is a question the lab must be able to answer.
  - **`linkedAt` uses `Timestamp.now()`, never `serverTimestamp()`** — Firestore rejects a sentinel inside an array element, at runtime, in production only.
  - Refuses: an id equal to the account's own `requester_id`, a missing/over-60-char label, more than `MAX_LINKS` (10) rows, and **any type other than `patient`** (23/09/2026).
  - **Never writes to the dossier holder's document.** Two accounts may point at the same `requester_id`; the holder loses nothing.
  - Emails the **dossier holder** (looked up via `users where requester_id == id`) that a relative can now read their results — best-effort, and only possible when the holder has an account carrying an email. `holderNotified` tells the screen whether anything was actually sent.
- **`adminUnlinkRequester(uid, requester_id)`** (≥staff) → removes one row, same transaction shape. Returns the fresh `links`.
- **`adminListRequesterLinks(requester_id)`** (≥staff) → `{accounts}` — who can read this dossier, each flagged `isSelf` (holder) or not (attached). Confusing a helper with the holder is the worst mistake possible at the counter.
- **`adminSetPractitioner({uid, requester_id, type, label, clear?, dryRun?, allowUnknown?, allowShared?})`** (**≥admin**, own file `functions/src/admin/adminPractitioner.ts`, 23/09/2026) → gives / removes an account's **doctor access** (`users/{uid}.practitioner = {requester_id, type, label, linkedAt, linkedBy, lastUsedAt?}`), which opens `/[lang]/mes-patients` — see `docs/pages/mes-patients.md`. Kept apart from `requester_id`/`type` on purpose: a doctor is usually also a patient, with relatives, and his patient identity stays untouched.
  - **Verifies the code against the lab server before writing** — `include_pdf:'none'`, **counts only** (`probe = {status: ok|unknown|error, dossierCount, patientCount}`), never a name. `dryRun: true` does the checks and writes nothing: it is what the card's « Vérifier » button calls.
  - Refuses: an invalid code (`^[A-Z0-9][A-Z0-9._-]{1,31}$` after canonicalisation to capitals without spaces), a `patient` type, a label outside 3–60 chars, a code equal to one of the account's patient ids (own or relative — it would be shadowed). **Needs explicit confirmations:** `allowUnknown` when the lab answers 404 (no dossier sent since the doctor's activation in Qalam), `allowShared` when another account already holds the code (owner's decision: allowed case by case, e.g. the doctor's secretary). A lab outage refuses with no override.
  - Writes in a transaction with **`update`** — the whole map when the code changes (a `set(merge)` would keep the previous code's `lastUsedAt`), only `type`/`label` when it is the same code. Removal = `FieldValue.delete()`.
  - Emails the account holder « Votre accès médecin est actif » on a NEW access (not on a label edit), best-effort, 10 s race. Returns `sharedWith` (other holders) and `pendingAccessRequest` (signup files a patient access request automatically — the card reminds the operator; nothing is decided for him).
  - Pure rules (`parsePractitionerInput`, `collidesWithPatientIds`, `activationRefusal`, `readPractitionerDTO`, `patientKey`) are unit-tested by `functions/scripts/test-practitioner-admin.js` (32 checks, run after `npm run build`).
  - `adminSearchPatients` returns `practitioner` on every result and also finds an account by its **doctor code** (case-insensitive, ranked exact) or by the access label. `adminTestResults` names the account holding a code for non-patient types (`practitioner.requester_id`).
  - Dashboard: `practitioners = {accounts, active (30 d), consultations30d, monthDays, monthReports, teamExcluded, list}` — one row per doctor from `listPractitionerRows()` (`functions/src/admin/practitionerDirectory.ts`, shared with `adminListPractitioners`), filtered by the same « Inclure les comptes de l'équipe » rule, most recent visit first; `consultations30d` still comes from the anonymous `usageDaily.practitionerConsultations`. The list has its own try/catch (falls back to the scan's counts). **A doctor-only account (no dossier, no relative) is excluded from the patient figures and from the relance list**: it would read as a patient awaiting activation, then as a dormant patient to call. A doctor who is also a patient stays in the patient figures.
- **Doctor requests** (`functions/src/admin/practitionerRequests.ts`, 24/09/2026): `requestPractitionerAccess` (any signed-in account — writes `practitionerAccessRequests/{uid}` pending + staff e-mail; grants nothing; records the doctor's confidentiality engagement on his account when the form carried the current version, and `engagementAt` on the request), `myPractitionerRequest` (auth), `adminListPractitionerRequests` (≥staff, returns `engagementAt`), `adminRejectPractitionerRequest` (≥admin). `adminSetPractitioner` marks the pending request `fulfilled` on activation.
- **Doctors holding an access** (`functions/src/admin/practitionerDirectory.ts`, 24/09/2026): `adminListPractitioners` (≥staff) → `{practitioners: PractitionerRow[]}` — every account with a VALID access (`practitionerIdentity`, the same test as `fetchResults`), queried by `where("practitioner.requester_id", ">", "")` (automatic single-field index), with its usage (`practitionerUsage/{uid}` via `getAll`), who activated it (names of the distinct `linkedBy`), `team`, `sharedWith`, the engagement. Never a name in a log line.
- **The engagement** (`functions/src/admin/practitionerEngagement.ts`): `acceptPractitionerEngagement({version})` (auth; only for an account holding an access; idempotent) — see `docs/pages/mes-patients.md` §10. `readPractitionerDTO` now returns `engaged` / `engagementAt`, shown on the « Accès médecin » card.
- `adminSetStaff(email, grant)` (≥admin) → set `role: 'staff'` / remove. Refuses if target is admin/owner.
- `adminSetAdmin(email, grant)` (owner only) → set `role: 'admin'` / remove. Refuses if target is owner.
- `adminListStaff()` (≥admin) → `{ members: [{uid,email,fullName,role}], callerLevel }`, sorted owner→admin→staff.
- `adminListDormant()` (**≥staff**) → `{ dormantList }` (uid, name, email, phone, `lastResultsAt`, `lastRelanceAt`) for the Relances tab. Same scan as the dashboard via the shared `scanAccounts()` helper, but served at staff level.
- `adminRecordRelance(uid)` (**≥staff**) → stamps `lastRelanceAt` + increments `relanceCount` when the front desk clicks "Relancer". Powers "relancé il y a X j" and the dashboard's return-rate metric.
- `recordShare()` (**any signed-in user**) → increments `usageDaily/{today}.shares`. Anonymous: nothing is written on the patient. Called by `ShareAccessCard` alongside the Analytics event (Analytics data isn't queryable from Firestore).
- `adminDashboardStats()` (**≥admin — no longer staff**) → the whole Tableau de bord in one call. Same bounded scan as `adminSearchPatients` (`SCAN_LIMIT`), **excluding team members** (any `role`) from the patient counts so the adoption denominator stays meaningful. Returns `totals` (accounts / withAccess / withoutAccess / pendingRequests / byType), `usage` (active in the last 30 d, dormant, `rate` = active ÷ withAccess as a %, `windowDays`), `latestCreated` (10, sorted on the ISO `createdAt` string), `latestActive` (10, sorted on `lastResultsAt`), `dormantList` (25 — access activated but never consulted or inactive > 30 d, never-used first, **includes `phone`** so staff can relance), and `truncated`. Timestamps come back as epoch ms.

Access requests (`resultAccessRequests/{uid}`, only touched via callables):
- `adminListAccessRequests()` (≥staff) → pending requests (`{uid, fullName, email, phone, createdAt}`).
- `adminFulfillAccessRequest(uid, requester_id, type)` (≥staff; **non-patient type ≥admin**) → merges identity onto `users/{uid}` + marks the request `fulfilled` (records `fulfilledBy`/`fulfilledAt`).
- `adminRejectAccessRequest(uid)` (≥staff) → marks the request `rejected`.
- Patient-side (not admin-gated): `requestResultsAccess()` creates a `pending` request; `myAccessRequest()` returns its status (used by `/resultats`). **Also fired automatically once per signup** by the login page (`autoRequestResultsAccess()`), so most `pending` requests now originate from signup rather than the button (Dr Aziz onboarding queue; see `docs/pages/login.md`).

### Staff email alert on every new request (août 2026, demande n° 18)
`requestResultsAccess` now emails the staff after writing the request, so nobody has to think about opening the Demandes tab. Same shared mailer as the CyberLab monitoring (`functions/src/email/mailer.ts`).
- **Recipients: `alertRecipients()`**, i.e. the `ALERT_EMAILS` string in `functions/.env` — **add or remove an address there, never in the code.** Deliberately NOT the `to`/`cc` list of `src/app/api/send-appointment/route.ts`: that is a different system (a Next.js route with its own transport), and duplicating the list would create two sources of truth. `replyTo` is the patient's own email so staff answer in one tap.
- Contents: name, phone, email, **origin** (`source`: signup vs the button on `/resultats`), date in Morocco time, account uid, and the admin-space URL. `todo` tells the reader to verify identity then fill in the `requester_id` in the Demandes tab.
- **The URL is a bare string inside a table row, not an `<a>`.** `renderAlertEmail()` escapes `footer` and every row value, so markup would render literally; Gmail and Outlook auto-link a plain URL anyway.
- **Pass RAW values to `renderAlertEmail()`.** It escapes everything itself — pre-escaping would put `L&#39;Allali` in the staff's inbox. `escapeHtml` is only for HTML you build *outside* the template.
- **Anti-duplicate is carried by the two existing early returns** (`already_granted`, `pending`), which sit before the write: a patient who re-clicks or simply logs in again triggers nothing. There is no `lastNotifiedAt` field. **So changing those early returns also changes the email de-duplication** — an implicit coupling worth remembering. No Firestore/Auth trigger was added either: signup already calls this callable, a trigger would double every mail.
- **Best-effort:** the whole block (including `alertRecipients()` and `APP_URL.value()`) is inside a try/catch, with a 10 s `Promise.race` so a slow SMTP cannot hold the callable open. A dead mailer must never stop a patient's request from being recorded. Only `uid` is logged — never the patient's email or phone.
- **Simulated mode:** with `SMTP_USER`/`SMTP_PASS` absent or placeholder, `sendMail` logs `mailer: SMTP not configured — simulated send` and returns as if sent. The function deploys and works before real credentials exist, and emulator runs stay inert.
- The callable declares `secrets: [SMTP_USER, SMTP_PASS]` and **keeps `REGION` = `europe-southwest1`** — the client calls `getFunctions(app, region)`, so changing it would create a second function and break every existing client.

CyberLab onboarding probe (`functions/src/cyberlab/adminTestResults.ts`, secrets `CYBERLAB_API_KEY`/`CYBERLAB_HMAC_SECRET`, URL param `CYBERLAB_API_URL`):
- `adminTestResults(requester_id, type, dossier_id?)` (≥staff) → calls `callCyberlab` (from `cyberlab/client.ts`) with the **client-supplied** id. Two phases like the patient bridge: no `dossier_id` → list only (`max_results:50`, `include_pdf:'none'`); with `dossier_id` → that single dossier's PDF on demand. **Scrubs** `patient_nom`/`patient_prenom` **only for `medecin`/`correspondant`** ids (a practitioner id would otherwise ship their whole nominative patient roster); a `patient` id keeps its name since that is the one person staff are confirming.
- **Identity shown to staff** (`patient_name` + `name_source` added to the response): the lab returns **empty names for `type:'patient'`** (data minimisation — verified on the real server, `docs/integrations/test-results.md` case A1), so the name normally comes from the **linked app account** — a best-effort `users` lookup `where('requester_id','==',id).limit(1)` returning `fullName` (never fails the test). `name_source` (`'lab'` \| `'account'`) is surfaced in the UI so staff are never led to believe the laboratory confirmed the identity. If Brahim ever returns names for patient ids, they take precedence automatically. Errors → generic French `HttpsError` (not_found→"not-found" = "aucun résultat", rate_limited→resource-exhausted, network→unavailable, else internal); logs `{kind,status}` only, never the body. Sets `Cache-Control: no-store`. Unlike `fetchResults` (identity from the profile), identity here comes from the client — hence the ≥staff gate.

**`requester_id` normalization (gotcha, fixed 2026-07-21):** Qalam displays large ids with a thousands separator, and a real patient profile was saved as `"67 305"` → the lab server answers `404 requester_not_found` and the patient sees **nothing** in `/resultats` (no error hinting at the cause). `normalizeRequesterId()` (exported from `functions/src/cyberlab/client.ts`, strips **all** whitespace incl. NBSP) is now applied on **write** (`adminSetRequester`, `adminFulfillAccessRequest`), on **test** (`adminTestResults`) and on **read** (`fetchResultsForUser`, so profiles saved before the fix are rescued at runtime without a data migration). Do not replace it with a plain `.trim()` — the problem is the *internal* space.

**Deploy note:** gen2 callables need `allUsers` as Cloud Run invoker (auth is enforced in-function). `firebase deploy` did not always apply it → the browser gets a CORS/403; grant it via the Cloud Run IAM API (see `functions/scripts` / conversation).

### « Le passer en dossier d'un proche » — a child's number typed as the parent's own (07/10/2026)

**The incident (06/10/2026).** A father who never had a test at the lab came with his daughter. He signed up; signup filed his own access request; the front desk validated it in the Demandes tab **with his daughter's dossier number**. It worked — he saw her results — but the app treated them as HIS: the home page's « votre dernier bilan », her number as HIS barcode on the profile, and his first own test would have overwritten the number (her results vanishing from his app). The right path for such a parent is the relatives card, where her dossier gets a label (« Ma fille — … »); an account with no dossier of its own and one relative opens straight on that relative (`resolveIdentities` / `authorizedIdentities` fall back to the first relative).

**The repair.** When the selected account HAS a main dossier, `LinkedRequestersCard` shows a dashed box (`data-testid="link-move-own"`): « Dossier principal de ce compte : N. Est-ce en fait celui d'un proche (son enfant, un parent) ? » → « Le passer en dossier d'un proche » opens a one-field form (« De qui s'agit-il ? », required) → `moveOwnToRelative(label)` in the page → **`adminLinkRequester({uid, requester_id: N, type: 'patient', label, fromOwn: true})`**. Server side (`attachRequester(..., fromOwn)`), ONE transaction: the id must STILL be the account's main dossier (else « Rechargez la fiche » — a stale screen must not empty a dossier someone just corrected), the relative row is added, and `requester_id` / `type` are deleted (`requesterLinkedAt` is kept — access WAS activated then). Without `fromOwn`, attaching the main dossier as a relative is still refused. Same holder notification as any attach (an account holding N as its own dossier, if any, is told a relative can read it). The page then clears the main-dossier field, patches the search results and shows `admin.link_moved`. Staff level, like every attach. The move box is opened on demand only: most main dossiers ARE the holder's.

**Prevention — « Accès pour : un proche » in the Demandes tab (08/10/2026, replaces the 07/10 hint).** Each pending access-request card starts with a choice (`data-testid="ar-for"`): **lui-même** (default, unchanged behaviour) or **un proche (enfant, parent…)**. Choosing « un proche » shows a label field (`ar-label`, « Ma fille — Rime » — what the account holder will see) and three one-tap proof chips (`ar-proof-*`: Parent d'un mineur = `autorite_parentale`, Proche présent = `present`, Procuration = `procuration`; nothing preselected — the proof says WHY access was given, which a single « vérifié » tick would not), and forces type patient. « Valider l'accès » stays locked, saying why (`ar-why`), until both are given. It calls **`adminFulfillAccessRequest({uid, requester_id, type: 'patient', forRelative: {label, proof}})`**: server side, `attachRequester` adds the relative (with proof, same rules as any attach), the request is marked `fulfilled` with `forRelative: true`, and the dossier holder (if he has an account) is notified like any attach. No refusal, no trip to the fiche. Chip colours are inline styles (the global button rules beat Tailwind colour utilities there). Page state: `arInputs[uid] = {requester_id, type, forRelative?, label?, proof?}` (`ArInput`). Covered by M22.

Covered by `scripts/test-practitioner-ui.js` M20 (the box, the locked confirm without a label, the exact payload with `fromOwn`, the success message, the emptied main-dossier field).

## Relative requests — the second queue in the Demandes tab

`RelativeRequestsSection` (`src/components/features/admin/RelativeRequestsSection.tsx`) renders **below** the access-request queue, in the same tab, visually separated. The tab badge counts both.

**Why a second queue rather than the same one:** "activate my own results" and "let me read someone else's record" are different decisions with different checks. Merging them would let the front desk treat the second like the first.

**The staff sees a name and a date of birth, not a dossier number.** The patient never supplies one — they do not know it, and asking would invite typing numbers until one works. The date of birth is what separates homonyms, which is why the patient form requires it.

**`proof` is mandatory to grant** (`present` / `procuration` / `autorite_parentale`). It is stored on the request **and** on the `LinkedRequester` entry. The real control — "does this person have the right to read that record?" — happens at the counter and cannot be moved into software; what software can do is record which proof was seen. Without it a link only says who created it and when, which answers nothing if the access is ever contested. `adminLinkRequester` (the direct path) accepts `proof` optionally; `adminFulfillRelativeRequest` requires it.

**Granting is gated on an actual probe.** `Rattacher` stays locked until the typed `requester_id` has been run through the Tester tab in this session (`testedIds` on the page). The patient supplied only a name and a date of birth, so **the name the lab returns is the only evidence the id belongs to the right person** — attaching without it opens a homonym's record to the wrong person, and nothing downstream would reveal it. The probe result is shown under the form, next to the requested name, with a red panel when the two look unrelated. **The comparison is a gate, not a hint** — corrected after the 18/09 test. `namesAgree()` compares the SET of words, ignoring order, case and accents, and **anything that is not the same set requires an explicit tick** ("Je confirme qu'il s'agit bien de la même personne") before `Rattacher` unlocks. Changing the dossier number clears the tick.

⚠ The first version compared only the **first word**, which inside a family is the family name: "EL ALLALI mohamed aziz" vs "El Allali Hassan" compared *equal*, so the warning never fired in the one situation it existed for — and `Rattacher` went fully active on the wrong dossier. A false alarm costs one click ("Mohammed" vs "Mohamed" will ask); a missed homonym opens a stranger's medical record. A failed probe does not count — the id stays locked.

**The two names are shown side by side, same size and weight.** They used to sit 250 px apart in different typography, which is how two names sharing a family name read as identical to someone in a hurry.

⚠ **Never put an early return above the message block.** `RelativeRequestsSection` had one for the empty list — and granting or refusing the LAST request empties the list, so the component took that branch and the confirmation message, correctly computed, was never rendered. Staff saw the card vanish in silence after handing someone access to a third party's medical record. The empty state is now part of the normal render, below the message.

**The locked button says why** (`rel_req_need_id` / `need_test` / `need_proof`). A grey button with no explanation is how staff conclude the screen is broken.

**`Refuser` sits on its own row, below a separator, as a quiet underlined link** — not beside `Rattacher`. Two buttons side by side, the second confirming in the same spot, is how a legitimate request gets refused by a double click.

**The dashboard tile counts both queues** (`pendingRequests = access + relative`, broken down by `pendingAccessRequests` / `pendingRelativeRequests`). It counted only the access queue at first, so the tab badge said 1 while the dashboard said 0 — a manager reading the dashboard would have concluded there was nothing to do.

**The label shown to the patient is the name the patient typed**, reused verbatim — no retyping at the counter, and it reads the way they expect.

Collection `relativeAccessRequests/{autoId}` (auto-id: one account may ask for several relatives, unlike `resultAccessRequests` which is keyed by uid). Fields: `uid, fullName, email, phone, relationship, relativeName, relativeDob, relativePhone, status('pending'|'fulfilled'|'rejected'), createdAt`, plus `requester_id, proof, fulfilledBy, fulfilledByEmail, fulfilledAt` on grant. **No Firestore rule was added**: the collection falls through to the default deny on purpose, and every access goes through a callable.

Callables: `requestRelativeAccess` (auth only, caps at 5 pending, de-duplicates same name + DOB, emails the lab), `myRelativeRequests` (auth only, the patient's own statuses), `adminListRelativeRequests`, `adminFulfillRelativeRequest`, `adminRejectRelativeRequest` (all ≥staff). i18n under `admin.rel_req_*`.

## Notes for AI
- **Not in public nav** — reachable only by URL (`/[lang]/admin`), gated as above.
- Role changes take effect in a client only after the profile re-loads (full refresh / re-login), since `AuthContext` caches `userProfile` for the session.
- Never write `users/{uid}` without `{ merge: true }` (holds `role`/`requester_id`/`type`/consent).
- Firestore rules keep `users/{userId}` client access to own-doc only, AND now **hard-block** clients from setting/changing the privileged fields `role`/`requester_id`/`type`/`lastResultsAt` (create rejects any of them; update rejects changing any — `diff().affectedKeys()`). These are written ONLY server-side (Admin SDK bypasses rules): the callables above, plus `fetchResults` for the usage stamp. This closes self-promotion to staff/owner, self-pointing `requester_id` at another patient's id, and forging one's own activity date. Do not loosen this — the role model, `adminTestResults` access, and the dashboard's integrity all depend on it.
- **Where the usage data comes from:** `fetchResults` (`functions/src/cyberlab/fetchResults.ts`) stamps it on the **list** fetch only — the one that runs when the patient opens the app — throttled to once per **6 h** (checked against the profile snapshot it already loaded, so no extra read) and wrapped in try/catch so usage tracking can never break a patient's results. In that same throttled block it writes `lastResultsAt`, sets `firstResultsAt` **once**, increments `resultsViewCount` (so the count means *sessions*, not calls), and bumps the anonymous `usageDaily/{YYYY-MM-DD}.consultations`. All dates/counters — never a result, never which dossier. `requesterLinkedAt` is stamped by `adminSetRequester`/`adminFulfillAccessRequest` at activation, which is what makes the "delay before first use" metric possible. Everything is declared to patients in `confidentialite.usage_*`.
- **`usageDaily/{YYYY-MM-DD}`** = `{ consultations, shares }`, a global tally linked to nobody. It is **absent from `firestore.rules` on purpose** → default-deny, Admin SDK only. It is the sole source for the weekly-activity chart and the share counter.
- **Gotchas fixed after the V3 launch, all three silent-wrongness bugs** (keep them in mind before touching these paths):
  - `usageDaily` must be read with `getAll()` on predictable day-id refs. `orderBy(documentId(), "desc")` needs a dedicated **descending** `__name__` index (Firestore only auto-creates ascending ones) and fails at RUNTIME with `FAILED_PRECONDITION` — invisible to `tsc` and to `next build`. That one 500'd the whole dashboard. The block is now in its own try/catch so a single missing metric can never blank the screen again.
  - `HBars` scales bar widths against the largest row, which is right for counts but wrong for a series that is **already a percentage** — the biggest value was always drawn full-width, contradicting the figure printed beside it. The age chart passes `scaleMax={100}`. Emptiness is still judged on the data, never on the fixed scale.
  - `dormantOf()` returns the **full** list; callers that render slice it themselves. It used to truncate at `DORMANT_LIST` (40), and the dashboard republished that length as a factual count — past 40 dormants it would have understated the backlog and contradicted the "Santé de la base" chart on the same screen.
  - The `resultAccessRequests` scan filters on `scopeUids` (the uids from `scanAccounts`, so it follows `includeTeam`). Request documents are keyed by the requester's uid; without the filter the team's own test requests inflated "Devenir des demandes", dragged the activation delay down, and could surface a colleague's name in the pending-request banner while the on-screen note claimed team accounts were excluded.
- **Looking at this page without an account:** `node scripts/preview-admin-dashboard.js`. /admin is behind auth **and** a role, so no headless browser can open it — yet layout is exactly what a type-check cannot see. The bench bundles the real `AdminDashboard` with esbuild, stubs only `react-i18next`, compiles the real stylesheet, and shoots four widths into the OS temp dir. It prints the two things that can be judged mechanically: horizontal overflow (must stay 0 on mobile) and the column count of the first chart grid (2 from 1280 px, 1 below). **It is not a test — nothing is asserted.** Its data is a hand-written fixture: a new field on `DashboardStats` renders as `undefined` there until the fixture is updated. Gotcha if you move it: the generated entry point lives outside the project, so esbuild needs `nodePaths: [<projet>/node_modules]` to resolve `react` — `absWorkingDir` does not do it.
- **Dashboard UI lives in components,** not in the page: `src/components/features/admin/AdminDashboard.tsx` (the 15 blocks, in the narrative order validated on the mockup) and `charts.tsx` (`AreaChart`/`VBars`/`HBars`/`StackedBar` — hand-built SVG/CSS, **no charting library in this project**, colours from the design-system tokens so both themes work). `RelancesTab.tsx` holds the front-desk list. `page.tsx` keeps state, callables and tab routing only.
- **Ramp-up caveat:** nothing was measured before the feature shipped, so every pre-existing account reads as "jamais consulté" until its owner next opens the app. The dashboard shows a `admin.dash_since` caption (module constant `USAGE_SINCE`) so the first weeks aren't misread — update that constant if the go-live date changes.
- **Adding a tool** = add a `TabItem` to `tabs` + wrap a section in `{activeTab === 'x' && …}`; `TabsNavigation` handles overflow, no layout change.
- Patient search by name/phone/DOB/`requester_id` is now implemented (`adminSearchPatients`, Patients tab). The per-search scan reads up to `SCAN_LIMIT` docs — fine for this lab; past a few thousand patients, migrate to a normalized-field prefix index or a search service (`truncated:true` is the early signal).
- Out of scope (future / Étape 2): traceability dashboard (accounts proposed/validated/dormant, filter by period + CIN — **CIN is not collected yet**), a "last results view" usage timestamp for the used/dormant indicator, account creation from admin, audit log of role/identity changes. Any usage tracking must store only an access timestamp, never medical content.
